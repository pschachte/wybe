# Wybe coding guidelines

These guidelines were initially generated by Google Gemini.  They will gradually
be evolved based on experience and taste (and to correct Gemini errors).

Wybe is not an opinionated programming language.  Wybe is actually quite
flexible regarding the order in which you write code, and the way you lay it out.  These are just suggestions.


## 1. Module Structure and Organisation

A Wybe source file represents a module. The top-level layout of a module,
or submodule should follow a predictable ordering to enhance readability:

  1. **Module Header / Documentation:** Comments describing the module's
     purpose.  After documentation, place the `constructors` (or
     `representation`) declaration, if the module provides a type.
  2. **Imports (`use` declarations):** Group all imported modules near the very top.
  3. **Public Interface (`pub`):** Explicitly declare public types, functions, and procedures first, defining the module’s interface.
  4. **Implementation Details:** Private helper functions, procedures, and data
     structures.  Submodules should also be written here, and the same ordering
     suggestions apply to each submodule.
  5. **Top-Level Execution Statements:** Code outside definitions runs
     immediately when the module/program is executed (such as `!println(...)`
     statements for main entry points) and should be cleanly sectioned at the
     bottom.


## 2. Spacing and Indentation

* **Indentation:** Use consistent indentation (recommend **4 spaces** per level; avoid hard tabs).
* **Blank Lines:**
  * Separate top-level definitions (types, functions, procedures, etc.) with **two blank lines**.
  * Separate internal blocks or logical groups of statements within a procedure with **one blank line**.


## 3. Procedure vs. Function Layout

Wybe sharply distinguishes between **functions** (pure, single-output,
expression-oriented) and **procedures** (imperative, stateful, potential side effects, and
statement-oriented). Their layouts reflect this difference:

### Functions

* Layout should favour single-line definitions for simple expressions using `=`.
* Multi-line functions utilising conditionals, `let`, or `where` clauses should wrap blocks cleanly:

```wybe
def square_root(x: float): float = 
    if { x < 0.0 :: 0.0
         else    :: core_sqrt(x)
    }

```

*

### Procedures

* Because procedures handle sequencing and imperative constructs, keep statement bodies cleanly scoped inside braces `{ ... }`.


## 4. Naming Conventions

* **Types:** PascalCase (e.g., `BinaryTree`, `CustomerAccount`).
* **Functions and Procedures:** snake_case (e.g., `calc_total`, `print_banner`).
* **Variables:** snake_case.


## 5. Layout

* 

* **Braces:** Place open brace on the same line as the construct that introduces
  it, such as `def` or `if`.  If the entire contents of the braces fit on one
  line, put the close brace at the end of the line.  If not, place close brace
  alone on a line, aligned with the start of the construct.
* **Conditionals (`if`):** Follow the open brace immediately with
  the first condition, without an intervening space.
  Align the vertical bar separating branches with the `if` and closing brace.
  Where conditions are short, align condition-consequent pairs
  vertically using double colons (`::`), separated on each side by a
  space.  Where conditions are longer, begin consequents on the next line,
  indented by 4 spaces.
   
```wybe
if {condition1 :: action1
|   condition2 :: action2
|   else       :: default_action
}
```

* **`let` and `where` Clauses:** Place binding statements on indented new lines to clearly separate local scoping from the core expression:

```wybe
let { 
    x = foo(a)
    y = bar(b) 
} in 
    x + y

```

* **Loops (`for` and `do`):**
* For bounded loops, place the iterator and body cleanly:

```wybe
for x in collection {
    !process(x)
}

```

* For unbounded `do` loops, maintain clear alignment of internal control statements (`while`, `until`, `break`):

```wybe
do {
    !step_engine
    while running
}

```

## 6. Comments and documentation

* **Documentation:** Place documentation for each `def`,
  `constructor`/`constructors`, `trait`, and `resource` declaration on the lines
  preceding the declaration, with no intervening blank lines.  Begin each
  documentation line with a single `#`.  Use markdown syntax within the
  documentation for highlighting.  Enclose parameter names within `backticks`
  when referencing them.
* **Submodule documentation** should follow the open brace of the `module` or `type` construct.
* **Line Comments:** Use `#` for single-line comments. Align inline comments cleanly to the right of code statements if brief, or on the line above for longer explanations.
* **Block Comments:** Use `#| ... |#` for temporarily commenting out blocks of code.
